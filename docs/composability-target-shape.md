# 组合性目标形态

这份文档描述 AgentM 的 atom 装载/卸载机制**应该长什么样**，不描述怎么从现状走过去。

它的用途是审查依据：每个碰到 `core/abi`、`core/runtime`、或 atom 契约的改动，都可以对着它问一句"这是在往这个方向走，还是在背道而驰"。

理论背景是 *A Programming Paradigm for Spatiotemporal Composability*（Cordis）。文档不假设读者读过论文。

---

## 0. 现状

这份文档写的时候，下面全部是"应该"。现在有一部分是"是"了。**它仍然是目标形态而不是实现说明**——但读它的人有权知道哪些句子已经描述现实。

| 概念 | 状态 |

| §9 · 全会话安装快照 | ✅ 已删。回滚是逆函数，一次安装写不进任何它不拥有的存储 |

| §9 · `ProviderRegistry` 私有 owner 表 | ✅ 已删。归属去问上下文树；离开时"它拥有哪些 provider"读的是**它自己带走的那张表**，不是按 owner 建的索引 |

| §3 · 层 | ✅ `services.layer`；AM026 拦住"读出来包一层写回去"的回归（含一行写完的那种写法）。**层是对键的修饰，不是对"我进来时看到的那个值"的修饰**——之后再 bind 一个新实现，仍然被现有的层包住；摘要按上下文数层数，因为折叠出来的值数不出来 |
| §3 · 单元型键第二个写入者是冲突 | ✅ 同秩两个原子绑同一个 **role** 直接报错，错误信息就是修复指令。范围限定在 role：普通 `register` 的 last-writer-wins 在这里是设计（遮蔽者离开时被遮的会重新露出），拒绝它会删掉 runtime 建在其上的行为 |
| §3 · 折叠在轮边界 | ⛔ **刻意不做**。每次读取折叠，而这在今天是安全的：runtime 里没有任何东西按工具调用重读服务——driver 消费的在 `start()` 抓一次，它重读的（工具、上下文策略、渲染器）在轮边界重读。为一个不存在的读者建缓存，正是这条线一直在删的东西。条件写进了 `services.layer` 的 docstring：**将来若要加"每次调用重读某个分层键"的读者，答案要在轮边界解析并按轮持有**，不是把这个 fold 变便宜 |
| §7 · 卸下别人的前置 | ✅ 装的时候查 `requires`，卸的时候以前什么都不查。现在会点名：谁还装着、少了什么、是谁走了。**报告而不是拒绝**——拒绝的是"没人选过的答案"（同秩争 role），这个答案恰恰是调用方要的；而且卸载是关停路径，关停和安装回滚都会走到 |
| §7 · `needs` / `after` 拆分 | ✅ 硬依赖那半仍叫 `requires`（改名会破坏所有已发布 manifest，而论文的论点是两个**职责**要分开，不是两个拼写）；`after` 是新加的、只管顺序、缺席不报错 |
| §6 · 上下文树 = 会话树 = 插件树 | ⛔ **只采纳前半句，后半句判定为错**。见下面 §0.1 |
| §5 · 补偿钩子 | ✅ `effect(..., compensate="...")`。跨出系统边界的写入（建的文件、起的容器、发出去的消息）现在有第三条路——以前只能把补偿动作**装成逆函数**交回去（于是所有恢复保证错误地覆盖了它），或者 `retain` 掉然后泄漏。它在同样的时刻跑、按同样的 LIFO 复合，**但不继承保证**：这里所有结论都是对着精确相等证的，含补偿的组合只恢复到作者自己定义的那个更粗的等价关系。摘要带上了这个字段，所以"两个摘要相等"在有补偿在场时说的话更少 |
| §11 · 明确不采纳的六项 | 仍然不采纳 |

### §0.0 这张表打过一次勾之后又发现的事

上面的 ✅ 是逐条验过才打的。后来又整体复审了一遍，发现**打勾的实现里有八处缺陷**，其中三处是线上可见的。记在这里，因为"验过"和"验全了"是两件事，而这张表本身正是靠"验过"立起来的。

- **层只在"某个层恰好是这个键最新的一次写入"时才折叠。** 之后再往这个键写一个值（第二个装的执行器 atom、配置解析完才绑边界的宿主、supersede 落下的新实现），那个值赢了写入序，折叠根本不跑，键上所有的层**静默失效**——写层的 atom 还装着、还被报告成在贡献。一个跑着但什么都没贡献的 atom，正是层这个机制存在的理由要消灭的东西。
- **拷贝拿走的是"赢的那条 entry"**，对分层键来说就是 `ServiceLayer` 本身——那是**修饰的指令**。子会话拿到它当服务用。
- **`bind` 把"这个键有层"当成"已经绑过了"**，于是给执行器加层就会让真正提供执行器的 atom 绑不上。层从不占那个格子。
- **拒绝一次写入不会把它撤回。** `refuse_contested_role` 跑在写入观察者里，观察者在写入**之后**才触发，所以只抛异常的拒绝是名义上的拒绝：调用方看到异常，表里的值还在。
- **`settle_ranks` 把上一次的秩带进来。** `after` 可以成环（它是偏好，没人拒绝这种组合），于是每次 link/unlink 都把这一对推深一层。秩变成了"这个会话经历了多少事"的计数——而秩正是组合用来排序那些它排不了序的东西的那个数。
- **supersede 之后再卸载，恢复时旧版本会回来。** 队列里那条未提交的安装被撤回了，可记录里还留着上一版的安装、且没有任何离开的记录。
- **`plan_mode` 是第三个"读出来包一层绑回去"的 atom**，包的是权限边界。AM026 只跟到赋值给局部变量的读取，一行写完的那种写不出来的它看不见——而那正是两种写法里更短的一种。
- **卸下别人声明的前置什么都不说。** 见上表。

八处里有五处在 `core/abi/services.py`，全部来自加层那一批改动。合计新增七个测试，每个都做了变异检查：把修复原地改回去，对应的测试必须红。

### §0.02 全目录压力测试找到的（第二轮）

上面那八条是逐文件复审找到的。之后又写了两个压力工具，**又找到六条**，其中四条是线上可见的，一条是我自己上一轮的修复引入的。

工具一：**把 28 个 shipped atom 一次全装上，再按随机顺序全卸掉**，比对摘要。逐个 atom 的清扫看不见交互——执行器那个 bug 要两个 atom 才成形，而一个 atom 不成链。八个随机顺序，全部回到起点。

工具二：**同一批 atom 换顺序装**，按"成员集合"比对（去掉顺序和每会话对象身份，剩下的才是"组合是不是同一个"）。

- **子会话的层翻倍了。** 子会话先拷贝父会话、再重放父会话的 atom，所以那些 atom 的贡献会**自己再来一遍**。普通 register 无所谓（重放的更新、替换掉拷贝的），层不行——层是复合。拷贝折叠结果（我上一轮的修法）会让子会话戴两层、孙会话戴四层。规则是"链接 vs 拷贝"往下一层：**拷贝目标推导不出来的，重放目标能推导出来的**。只有真的 spawn 一个子会话才看得见，而且要两代——深度 1 上重放自己的写入赢了写入序，把拷贝盖住了。
- **两个 provider atom 都把 retry policy 焊死在构造里，且什么都没声明。** 把 provider 列在 `retry_policy` 前面，provider 已经造好了、没人重建，这个会话此后**每一次模型调用都没有重试**，静默。而 `retry_policy` 自己的描述就写着"consumed during provider construction"——耦合是知道的、写在散文里、写在任何机器读得到的地方都没有。这正是 `after` 的用途。
- **`requires` 在"已创建但没 start"的会话上谁都不查。** 组合时求解器排序，运行时 `_verify_runtime_requirements` 检查，中间这个洞什么都没有。`llm_compaction` 装进空会话照样成功，然后**比自己 manifest 宣称的少注册一个能力**。原来那条独立测试之所以通过，正是因为 atom 悄悄降级了。
- **分层键的归属跟着历史走。** 绑定按写入序解析，层按 `(rank, 写入序)` 折叠，而归属把两者塞进同一场写入序竞赛。`tool_executor` 由两个图**能**排序的 atom 分层，可索引报的 owner 取决于谁最近重装过。
- **`ExtensionSpec` 旁边再传一个 config 会被静默丢掉**，表现成 atom 因为"缺一个你确信传了的字段"拒装。
- **前置离开的告警点错了名**：它报的是"这次被卸掉的那个"，而不是"真正把能力带走的那个"，而且之后每卸一个都重报一遍。

### §0.03 真实模型端到端跑出来的（第三轮）

拿真模型跑 CLI、多轮、工具、fork、并发子会话、中断、恢复，又找到两条：

- **`SessionReadyEvent` 是 runtime 唯一告诉 atom "把活推迟到这里做"的地方，而它没法做异步的活。** 它是 `emit_sync` 发的，所以 `async def` 的处理器**一次都没跑过**——总线关掉协程、打一行 "async handler skipped"、继续走。`skill_loader` 的全部工作就在这个处理器里，所以**任何跑过的会话都没有 skill**：系统提示里什么都没注入，`load_skill` 无论磁盘上有什么都回答 "(none)"。让模型用一个明明在磁盘上的 skill，它跑去 grep 文件系统绕过去了——44.8k prompt token，还在回答里自己说了这件事。改成 awaited 之后它直接调 `load_skill`，24.3k。

  代价是投递时机从"`start()` 返回前"变成"第一轮之前"，而 `atom_watch` 的交接机制正建立在"ready 只发一次，运行中装进来的版本接不到"这句话上。所以运行时安装现在会等这次通告——那句话从**碰巧成立**变成**被强制成立**。
- **OTel 的 `Status(UNSET, description)` 会被丢掉并告警。** 强制关闭 span 的理由本来要记在那里，结果每个会话都打一行 "description should only be set when status_code is set to StatusCode.ERROR"，而它告警的那个理由本身被扔了。

### §0.1 为什么会话不并进同一棵树

文档 §6 说"上下文树 = 会话树 = 插件树"。原子上下文那一半做了；**会话那一半是错的**，这里写下理由，免得以后有人当成待办来"补全"。

分界是一句话：**链接是给共享生命周期的东西，拷贝是给共享起点的东西。**

一个原子的上下文**是**会话的一部分——解链就是它离开的方式，它活不过它的会话。所以链接对：写落在自己家、读向上解析、拿走它就等于它没来过。

子会话不是父会话的一部分。它是**另一个工作单元**，父会话是它的**前驱**而不是容器。而且这个仓库有**两种**造它的方式，两种都说的是同一件事：`spawn` 派一个新 agent 去干活，`fork` 从某个点分叉一条既有的——**没有一种的意思是"然后继续跟着我变"**。

所以子会话在创建时拷贝父会话的 tree-scoped 边界，然后各走各的。父会话之后绑的东西不会到达一个已经在干活的子 agent。

顺带这也让"两份账"那条批评在这里**不成立**：拷贝之后没有任何人声称要保持同步，那就不是同一个事实的两份账，**那是一个新事实**。看不见后续变化不是漂移，是分叉。

（链接版我实现出来验证过可行——scope 过滤放在跨会话的那条链接上，`scope="session"` 保持原义——然后回退了。可行不等于正确。）

## 1. 诊断

现状不优雅，根源是一次方向搞反的设计：

> **平台枚举"atom 能干哪几类事"，然后按这张清单去清理。**

这张清单的副本散落各处：六个 `register_*` 方法、`AtomRegistrations` 的五个固定格子、`ProviderRegistry` 私有的 owner 表、presenter 专用的 `register_cleanup`、以及"用 `SessionShutdownEvent` 做收尾"这个约定。

清单外的东西——atom 起的后台任务、开的连接、打的补丁——平台看不见，也收不回。

目标形态把方向反过来：

> **平台不枚举任何东西。它只要求：你改了什么，就交出怎么撤销。**

---

## 2. 一个上下文，三个概念

### 概念一 · 键

所有共享的东西挂在一个命名空间下，每样东西是一个**有名字的槽位**。

工具是键 `tools`。事件通道是键 `bus:<channel>`。模型 provider 是键 `provider`。服务就是它自己的键。

今天这些各有各的存储、各有各的删除路径、各有各的排序规则。它们本质是同一种东西，应该只有一套机制。

### 概念二 · 带逆的写入

往任何键上写，只有一个入口，而这个入口**必须返回撤销方法**。

由此：

- "某个 atom 拥有什么" = 打了它标记的那些写入。不需要单独的账本表。
- 卸载 = 倒着跑一遍它的逆。
- 安装失败回滚 = 同一个动作，跑的是**实际已经执行过**的那部分逆。
- 会话关停 = 同一个动作。

三条今天并存、覆盖面还不一样的回收路径，塌缩成一条。

### 概念三 · 秩

谁在谁前面，由**依赖图**算出来，不由谁先装决定。

这是"重装一个 atom 不牵连它后面所有人"的前提。只要执行顺序还是写入顺序的函数，改动一个位置就必然要重建它之后的一切——今天 `atom_watch` 的后缀重装就是在补偿这一点。

---

## 3. 键只有两种形状

这是把"可交换性"从**纪律**变成**类型**。

### 集合型键

内容是无序集合：工具、同优先级的事件处理器、provider 列表。

加进去的东西互不干扰，从中间抽走任何一个都安全。这是白送的性质——不需要任何额外假设。

**判据**：这个键对外公开的所有读操作里，有没有一个能区分"先 A 后 B"和"先 B 后 A"？没有，就是集合型。

### 单元型键

内容是单个值：模型、执行器、权限策略。

第二个写入者是**冲突**，应该报错，不应该默默覆盖。今天 `ServiceRegistry.bind` 已经做对了（重复绑定抛错，除非显式 `replace=True`），而 `register` 是 last-writer-wins——同一个抽象下两种语义，这本身就是 bug 来源。

### 层：单元型的正确出口

当多个 atom 确实都想影响同一个单元型键（执行器装饰器是典型），正确做法**不是**"读出来包一层再写回去"——那样删掉任何一层都会把整条链带走，你们的 `remove_atom_registrations` docstring 已经把这个限制写下来了。

正确做法是：每一层写**自己的私有键**（一键一写者，于是自动是集合型），runtime 把公共键绑到一个稳定门面，按秩折叠所有层。

于是"从中间抽掉一层"变得可表达。今天它不可表达。

### 折叠在轮边界，不是每次调用

层的折叠结果必须在**轮边界**重新解析，不能每次调用都重折。否则一个运行时装入的权限层会在同一轮的两次工具调用之间生效——一次转换跑在两套不同的依赖解析上。

这条不是洁癖：`Session.install_extension` 的文档已经写明"运行时装入的 atom 不能改变正在跑的那一轮已经广告出去的工具表面"。同一条不变量，推广到所有分层的键。

## 4. 为什么不是 `install` / `uninstall` 配对

这是每个读者都会问的问题，也是几乎所有插件系统的做法（VSCode 的 `activate`/`deactivate`、OSGi 的 deactivate 回调、以及本仓库今天用 `SessionShutdownEvent` 做收尾的约定）。

它不成立，理由是结构性的：

**它不复合。** 如果 `install` 是拼出来的——调了公共的辅助函数、跑了循环、复用了别的模块——那 `uninstall` 必须手工镜像这个结构。抽一个 `_setup_storage()` 给三个 atom 用，三个 atom 的 `uninstall` 各自都得知道它干了什么。而逐个效果自带逆时，**复合的逆是推导出来的**，永远不用写：辅助函数自己带着逆，谁调它谁免费获得清理。

**它处理不了半途失败。** install 在中间炸了，前面已执行的哪些要撤？`uninstall` 不知道，它是照"install 跑完了"写的。所以必须再搞一套失败回滚——这正是本仓库今天同时拥有账本和全会话快照、且两者覆盖面不同的原因。累加器一个东西同时解决两者，因为它持有的正好是**实际执行过**的那些逆。

**它处理不了顺序。** LIFO 靠作者自觉。累加器构造上就对。

**它处理不了运行时才产生的效果。** install 注册的 handler 后来又建了个连接；写在编码期的 `uninstall` 不可能知道。累加器知道。

**没有任何东西强制它存在或正确。** 空的 `uninstall` 能编译，错的也能编译。而"注册了但不给逆"在目标形态里**根本写不出来**——是类型错误，不是纪律问题。

**本仓库已有现成反例**：`atom_watch` 用 `SessionShutdownEvent` handler 取消自己的轮询任务，而 `bus.remove_owner` 恰好在需要它的那一刻删掉这个 handler。配对式收尾在这里不是"没写好"，是结构上到不了。

### 配对是对的，粒度错了

应该配对的是**每个原子操作 ↔ 它的逆**，不是组件 ↔ 组件。

配好之后，组件级的 uninstall **自动存在**——它就是"倒着跑这个 atom 累积的所有逆"，只是没人手写。

---

## 5. 补偿：显式钩子唯一该活下来的地方

有些操作没有逆。

创建的文件、启动的沙箱容器、发出去的消息、已经计费的 API 调用——它们跨出了系统边界。能做的只有两件事之一：**扣留**（推迟到状态确定再发出）或**补偿**（做一个弥补动作：删掉创建的文件、杀掉起的容器）。

补偿**不是**逆。它恢复的是一个更粗的、由应用自己定义的等价关系。所以：

- 它必须显式声明，且**语法上长得和逆不一样**，免得读代码的人混淆
- 它按同样的 LIFO 顺序复合（这一点和逆一致）
- 但**任何关于"任意顺序撤销"的保证都不适用于它**——那些结论是对着精确的等价关系证的，换成粗的必须重新论证

命名上叫 `compensate`，不叫 `uninstall`。它应该很少见；每出现一次，都意味着那个位置在系统边界之外。

---

## 6. 上下文树 = 会话树 = 插件树

今天有两棵树：会话树（spawn 子会话）和插件树（atom 装 atom），两套记录、两条移除路径。atom 装的 atom 在卸载时成孤儿，直接原因就是第二棵树没有父指针。

目标形态只有一棵：**上下文树**。

派生一个子上下文——可以是开一个 subagent，也可以是装一个 atom——是同一个动作。子上下文的写入记在自己名下，父上下文倒下时连带倒下。

一个机制，两种用法。

### 父指针取自"谁在安装"，不是"谁在调用"

这一条必须踩准。父指针的正确来源是**安装栈上的那个 atom**，不是"谁的代码触发了这次安装"。

反例：`atom_watch` 在自己的任务里重装整条尾巴。如果父指针取自调用者，`atom_watch` 就成了整个 scenario 组合的父节点，卸载它会连带摧毁整个会话。

### reload 重新挂载，不级联删除

替换一个 atom 时，它的子节点应该**重新挂到替换者**，而不是被级联删除。否则编辑一个装了工具的 atom 会删掉它装出来的所有东西。

---

## 7. 依赖声明拆成两个词

今天 `requires` 一个词干两件事：既是"没有它我跑不了"的满足性检查，又是拓扑排序的输入。

后果是**没法声明可选依赖**——一声明就变成硬依赖加一条排序边。于是仓库里所有刻意的可选读取（探测不到就降级）只能不声明，反过来让声明本身不可信：读一个 atom 的 manifest，你并不知道它实际会碰什么。

拆开：

- **`needs`** —— 硬依赖。管满足性，也管排序。缺了就装不上，报错信息是一条修复指令。
- **`after`** —— 只管排序。"如果它在，我排在它后面"，不要求它存在。

两个词，那个死结就散了。而且 `after` 正是"把顺序敏感的部分交给声明去承载"这条原则的落地——顺序不再是注册时序的副产品。

## 8. atom 作者看到的形态

优雅不该以作者的负担为代价。目标形态下的 atom 和今天几乎一样：

```python
MANIFEST = ExtensionManifest(
    name="my_atom",
    description="...",
    needs=(STORE_ROLE.capability,),          # 硬依赖
    after=("atom:system_prompt",),           # 仅排序
    provides=("service:my_thing",),
)

def install(ctx, config):
    ctx.tools.add(my_tool)                   # 集合型键，自带逆
    ctx.on(SomeEvent, handler)               # 同上
    ctx.provide(MY_THING, Thing())           # 单元型键，重复写入报错
    ctx.layer(TOOL_EXECUTOR, wrap)           # 层，可以从中间抽走
    ctx.task(my_loop())                      # 后台任务终于有地方放
    ctx.effect(open_and_close_something)     # 逃生舱：平台不认识的东西
    ctx.compensate(delete_the_file_i_made)   # 不可逆的东西，显式且刺眼
```

关键性质：**没有任何一条不被追踪的路径。**

今天 `register_tool` 被追踪而 `asyncio.create_task` 不被追踪，所以"禁止 atom 文件里裸用 `create_task`"这条 lint 规则显得很任意。反过来之后，**API 表面就是被追踪的表面**，那条规则才讲得通——它不再是禁令，而是"用这个更好的入口"。

## 9. 这个形态删掉了什么

判断它是否真的优雅，唯一标准是**加的比删的少**。

- `AtomRegistrations` 的五个固定格子，以及按类型分支的那一大段删除代码
- 全会话安装快照（`_capture` / `_restore_extension_install_state`）
- presenter 专用的 `register_cleanup`
- "用 `SessionShutdownEvent` 做 teardown"这个约定
- `ProviderRegistry` 私有的 owner 表
- 事件总线的 seq 作为**跨 atom** 的排序输入（作为 atom 内部 tiebreak 保留）
- context policy 那张 `id()` 键的优先级映射
- `atom_watch` 的后缀重装，以及它私有的 `_applied` 信念
- "包裹服务的 atom 不是 supersede-safe" 这条限制本身

## 10. 审查依据

拿这份文档审 PR 时，问这几个问题：

1. **这个改动是在增加一个新的"平台知道怎么清理的东西"的类型吗？** 是的话，方向错了——应该让它成为一次带逆的普通写入。
2. **它引入了第 N 张 owner 表吗？** 归属只应该有一处。
3. **它让某个执行顺序依赖于装载顺序吗？** 顺序应该来自依赖图。
4. **它给一个单元型键加了第二个写入者吗？** 要么报冲突，要么改成层。
5. **它新增了一条不被追踪的副作用路径吗？** 后台任务、文件、连接、子进程——有没有走 `ctx.` 下的入口。
6. **它把 teardown 写在了远离对应 setup 的地方吗？** 逆应该紧挨着它要撤销的那次写入。
7. **它声明的和它实际写的一致吗？** manifest 应该是真话，且这件事应该被机械检查而不是靠自觉。

## 11. 明确不在这个形态里

以下是论文里有、但**刻意不采纳**的东西，附理由。写在这里是为了避免以后有人"补全"它们。

**完整的响应式生命周期状态机**（Inactive/Reloading/Active/Unloading、target view vs committed view、动态的撤回守卫）。它的四个精化里，三个回答的是本项目没有的问题：安装是一次调用而不是可恢复的迭代器；组合变更者只有一个，一把锁就够，不需要并发卸载协议；失败路由单靠累加器就买到了。唯一买到真东西的是撤回排序，而它真正需要的地方（会话关停时消费 atom 提供的 environment/telemetry）可以**静态放电**——因为安装序本来就是拓扑序，按反序 revert 即可。引入状态机会让会话同时拥有两套生命周期概念。

**响应式激活**（依赖不满足就静默待命，等它出现自动激活）。组合期已经能算出有效激活序并拒绝环，没有留给运行时去发现的到达顺序。而且对于 atom 由 agent 生成的场景，**抛错就是产品**：一条"X 需要 Y 但 Y 不存在"是修复指令；一个静默待命的 atom 是行为缺席，agent 只能从"模型没调那个工具"里反推。

**撤回级联**（移除 provider 时传递性地撤回它的消费者）。它会制造静默分歧：跟随器会认为 scenario 已应用，而被级联掉的 atom 永远消失。今天的悬垂失败是响亮可读的，静默的多 atom 拆除是可读性上的倒退。

**进程内的能力隔离**（拒绝 atom 读取未声明的键）。它在 Python 里买不到安全性质——语言级中介已经被击穿：`_AtomAPIFacade` 的名字改写槽位可以被一次普通属性访问绕过，而且有服务把已授权的能力闭包当普通值发布出去。真正的隔离属于 agent-env 的沙箱边界。保留的是这件事**诚实**的那一半：让声明成为真话并机械检查，这样审阅组合的人读到的是真的。

**realm / 隔离表**（同一个键在不同上下文解析到不同值）。会话本身已经是 realm——每个会话拥有自己的注册表，子会话拿到的是独立副本。再加一层会有两套"这个键解析到哪"的机制要保持一致。更硬的是：runtime 自己就消费共享的那些键，隔离它们会让宿主失能而不是约束客体。

**访问时拦截的元数据机制**。权限策略已经占着这个位置，且已经是异步的、可替换的、在工具路径上的。缺的只是访问者身份，那是一个字段的事，不是一个子系统。
